Introduction — What We Built

This project is a design pattern demonstrating how to verify the identity of an AWS Nitro Enclave from a web browser and establish an end-to-end encrypted channel — all without trusting any intermediary server.

The application walks users through a 3-step interactive wizard:

The 3-step wizard flow: attest → verify → encrypt

🔒 Generate Attestation

Request a cryptographic attestation document from the Nitro Enclave, with an optional nonce for freshness protection.

✅ Browser Verification

Verify the COSE signature, certificate chain to AWS root CA, PCR values, and extract the enclave's public key — entirely client-side.

🔐 HPKE Secure Message

Encrypt a message with HPKE (RFC 9180) using the verified public key. Only the enclave can decrypt it. Receive an encrypted response back.

🏗️ Fully Automated Infra

One CDK deploy creates everything: VPC, EC2, API Gateway, Cognito, CodePipeline, Amplify. Push code and it flows to production.

💡 Key Insight

On the parent instance there is no application backend — only a thin TCP-to-vsock proxy that forwards bytes to the enclave and cannot decrypt them (it does not hold the enclave's private key). Trust is established directly between the browser and the hardware-attested enclave.

What Are AWS Nitro Enclaves?

Nitro Enclaves are isolated compute environments that run on a parent EC2 instance. They have no network, no storage, and no human access — making them ideal for processing highly sensitive data.

Runs on AWS Graviton

AWS Nitro Enclaves is processor agnostic and is supported on most Intel, AMD, and AWS Graviton-based Amazon EC2 instance types built on the AWS Nitro System. This solution runs on AWS Graviton (c8g.large). Because Graviton has no simultaneous multithreading (1 vCPU = 1 physical core), the enclave is allocated a single vCPU and 2 GiB, leaving 1 vCPU and ~2 GiB for the parent instance.

PCR Values — Measuring Enclave Identity

Platform Configuration Registers (PCRs) are SHA-384 hashes that measure different aspects of the enclave. Any change to the enclave's code produces different hashes — this is how you know exactly what's running inside:

PCR What It Measures Changes When…
PCR0 Enclave Image File (EIF) Any file in the enclave Docker image changes
PCR1 Linux kernel + bootstrap Kernel or init process is updated
PCR2 Application code Your Python/application code changes
PCR3 IAM role of parent instance EC2 instance role assignment changes
PCR4 Instance ID Running on a different EC2 instance
PCR8 Signing certificate EIF is signed with a different key
🔒 Security Guarantee

By pinning expected PCR values, you can cryptographically verify that the enclave is running exactly the code you expect. If an attacker modifies anything, the PCRs won't match.

The Attestation Flow

Attestation is the process of proving to a remote party what code is running inside the enclave. Our implementation performs all verification in the browser — nothing on the server side is trusted with validation decisions.

Why the root certificate is pinned in the app

The browser verifier ships with the AWS Nitro Enclaves root certificate pinned in the client, rather than fetching it at runtime. AWS publishes the root as a zip at https://aws-nitro-enclaves.amazonaws.com/AWS_NitroEnclaves_Root-G1.zip (S3 behind CloudFront), but that endpoint sends no Access-Control-Allow-Origin header, so a browser cannot fetch it cross-origin — and because it is AWS-owned, we cannot add CORS to it. Since the root is a long-lived trust anchor (valid for 30 years), pinning it in the app is both practical and the stronger posture: a pinned root cannot be substituted by a compromised network path or backend, which is the whole point of verifying client-side. To confirm or rotate it, download the zip and verify its SHA-256 fingerprint against the value AWS publishes.

References: AWS Nitro Enclaves Root-G1 (zip)  ·  Verifying the root of trust (AWS docs)

HPKE — End-to-End Encryption with the Enclave

We use Hybrid Public Key Encryption (HPKE, RFC 9180) to establish a secure channel directly between the browser and the enclave. The parent's TCP-to-vsock proxy relays encrypted payloads but cannot decrypt them.

The shared secret is never transmitted — both parties independently derive it from the Diffie-Hellman exchange. An eavesdropper sees public keys but cannot compute the secret without the private keys.

HPKE Suite

Component Algorithm Purpose
KEM DHKEM(P-256, HKDF-SHA256) Key Encapsulation — ECDH on P-256 curve
KDF HKDF-SHA256 Key Derivation with labeled domain separation
AEAD AES-128-GCM Authenticated encryption of payloads

How HPKE Works — The Encryption Dance

⚠️ Security Note

Always obtain the enclave's public key from a verified attestation document. Never trust an unauthenticated endpoint for the key — the attestation signature chain proves the key belongs to the authentic enclave.

⚠️ Defense in depth: the last network hop is HTTP

In this sample, the leg from API Gateway through the VPC Link and internal Network Load Balancer to the inbound proxy on the EC2 instance (port 8000) is plain HTTP. It stays within a private, isolated VPC (no internet or NAT gateway), and the sensitive payload is already sealed to the enclave with HPKE — so only HPKE ciphertext and the public attestation document cross this hop. This is a deliberate simplification of the sample. Some threat models legitimately require transport encryption on every hop, so treat this as a real assumption to evaluate for your environment, not something to dismiss.

Recommended mitigation: terminate TLS on the instance (ideally inside the enclave) with a certificate issued by a public (trusted) certificate authority for a hostname you control, keep the NLB as a TCP :443 passthrough, and set TlsConfig.serverNameToVerify on the API Gateway integration. A publicly issued certificate is required because API Gateway HTTP APIs (v2) always validate the backend certificate against trusted CAs (their TlsConfig has no verification-skip option); accepting a self-signed certificate would instead require REST APIs (v1) with insecureSkipVerification.

Debugging on the instance

The EC2 instance runs in a private isolated subnet with no inbound SSH. All on-instance debugging is done over AWS Systems Manager (SSM) Session Manager. CodeDeploy manages the services; the commands below are for inspection and manual recovery — they are not part of the deploy flow.

Terminal Start a session 
# Find the running instance (the Auto Scaling group keeps desired=1)
INSTANCE_ID=$(aws ec2 describe-instances \
  --filters "Name=tag:Name,Values=*NitroAttestation*" "Name=instance-state-name,Values=running" \
  --query "Reservations[0].Instances[0].InstanceId" --output text)

aws ssm start-session --target "$INSTANCE_ID"
On the instance (via SSM) Inspect the enclave and services 
# Enclave state (expect one enclave in the RUNNING state)
nitro-cli describe-enclaves

# systemd services: the launcher (runs the enclave) and the inbound proxy
# (TCP :8000 NLB target -> vsock into the enclave)
sudo systemctl status enclave-launcher
sudo systemctl status enclave-inbound-proxy
sudo journalctl -u enclave-launcher -f
sudo journalctl -u enclave-inbound-proxy -f

# Health and attestation, hitting the proxy -> enclave locally (no auth on the
# in-VPC hop; the JWT is enforced at API Gateway)
curl -s http://localhost:8000/health | jq
curl -s -X POST http://localhost:8000/api/attestation \
  -H "Content-Type: application/json" \
  -d '{"nonce": "test-nonce-123"}' | jq '.status, .size_bytes, .hpke_suite'
On the instance (via SSM) Restart / recover 
# Restart the enclave and proxy (CodeDeploy normally does this on deploy)
sudo systemctl restart enclave-launcher
sudo systemctl restart enclave-inbound-proxy

# Stop everything and terminate the enclave
sudo systemctl stop enclave-inbound-proxy enclave-launcher
nitro-cli terminate-enclave --all

# Reinstall the unit files after editing them under /opt/nitro-attestation/systemd
sudo cp /opt/nitro-attestation/systemd/*.service /etc/systemd/system/
sudo systemctl daemon-reload

# Launch the enclave manually for debugging (attaches the console; CPU/memory
# come from the CodeBuild-generated metadata.json)
CPU=$(jq -r '.cpu_count // 1' /opt/nitro-attestation/metadata.json)
MEM=$(jq -r '.memory_mib // 2048' /opt/nitro-attestation/metadata.json)
nitro-cli run-enclave --eif-path /opt/nitro-attestation/attestation-enclave.eif \
  --memory "$MEM" --cpu-count "$CPU" --enclave-cid 16 --attach-console

Clean Up

Terminal Destroy All Resources 
# Empty S3 bucket first
BUCKET=$(aws cloudformation describe-stacks --stack-name NitroAttestationStack \
  --query "Stacks[0].Outputs[?OutputKey=='EifBucketName'].OutputValue" --output text)

What's Next?

This reference implementation demonstrates the core patterns. For production use, consider:

  • WAF — Add AWS WAF to API Gateway for rate limiting and DDoS protection

  • Multi-region — Deploy to multiple regions with Route 53 failover
